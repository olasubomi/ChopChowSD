# Gmail API sender setup (CCD-490)

This integration sends Chop Chow transactional emails using Gmail API HTTPS rather than Gmail SMTP.

## Google Cloud (owner action)

1. In the **same Google Cloud project** where Gmail API is enabled, open Google Auth Platform.
2. Use the dedicated **ChopChow Gmail API** OAuth 2.0 Web application client. Do not reuse the customer Google Sign-In client.
3. Under Data Access, authorize only `https://www.googleapis.com/auth/gmail.send`.
4. Under Audience > Test users, include `chopchowsd@gmail.com` while in Testing.
5. For one-time manual authorization, add **`https://developers.google.com/oauthplayground`** to this client's **Authorized redirect URIs**. This is a Google-operated testing tool, not a production backend endpoint.
6. Visit https://developers.google.com/oauthplayground, open the gear icon, select **Use your own OAuth credentials**, and enter this client's ID and secret **only in the official Google OAuth Playground**. Select the Gmail send scope, authorize as `chopchowsd@gmail.com`, and exchange the authorization code for tokens.
7. Copy the resulting **refresh token directly into Render's secret environment-variable editor**, not into a repository, issue, PR, screenshot, chat, or logs. The refresh token belongs to the sender account, not to the account resetting its password. Keep the client secret in Render as well.
8. After setup, consider removing the OAuth Playground redirect URI to reduce the client's authorization surface. No application callback route is needed for ongoing token refresh.

**Testing-mode caveat:** For External OAuth apps requesting Gmail scopes, refresh tokens typically expire after seven days in Testing. Do not rely on this for production. Plan the transition to In production, review any Google OAuth verification requirements, and test refresh-token longevity before enabling critical live password recovery. The API being enabled does not by itself grant send permission.

## Render backend environment

Set these variables in the **correct ChopChowSD service**, not the frontend or the non-live service:

- `GMAIL_OAUTH_CLIENT_ID`: the dedicated Gmail API client ID
- `GMAIL_OAUTH_CLIENT_SECRET`: the dedicated Gmail API client secret
- `GMAIL_OAUTH_REFRESH_TOKEN`: sender's authorized offline refresh token
- `GMAIL_SENDER_EMAIL`: `chopchowsd@gmail.com`

Do not commit real values. Do not deploy before the OAuth credentials have been securely configured and a staged email delivery test succeeds.

## Behavior and validation

- All existing mailer functions call the Gmail API HTTPS transport.
- MIME email is generated by Nodemailer locally, without opening an SMTP connection.
- A successful API response means Gmail accepted the message, not that it arrived in the recipient's inbox.
- Network failures and API errors reject the send operation. Avoid blind retries after an ambiguous timeout because that can send duplicate emails.
- The password-reset request must await the send operation and not claim success on delivery failure (dependent on draft PR #219).
- Test with `node --test tests/gmailApiTransport.test.js` after installing dependencies.
- In a controlled preview, test reset request, Gmail acceptance, inbox receipt, reset link, token expiry/single-use behavior, successful login, and no tokens in logs.
- Keep email and OAuth errors free of secrets, reset links, and message bodies.
